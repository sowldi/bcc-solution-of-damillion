### Что считать подтверждённым, гипотезой и непроверенным

Это главный источник ошибок этапа — определения должны быть явными в коде и в README.

- **Подтверждённый дефект** — замечание со статусом `verified` с важностью `major` или
  `minor` из `LintResult.findings` и `QualityResult.findings` (CTR-01, CTR-02, ACC-01).
  - Важность `info` (например, CON-02 «похожие формулировки», XRF-01 «явная ссылка») —
    **не дефект**, а повод для проверки или справка о связи.
  - Ребро Fact Graph `depends_on` — не дефект.
- **Подтверждённое противоречие** — только `Contradiction` со статусом `confirmed` из
  `QualityResult` (CTR-01 или CON-03 с несовместимыми значениями).
  - Внимание: замечание CTR-02 имеет `evidence_status="verified"` (доказаны цитаты), но
    противоречие по нему — **потенциальное**; CON-03 — подтверждённое замечание правила, но
    противоречие может быть потенциальным (значения совместимы).
  - Статус противоречия брать из `Contradiction.status`, а не из `evidence_status`.
- **Гипотеза** — любое замечание `origin="llm"` (`unverified`) и любое потенциальное
  противоречие. Гипотезы **не входят** в счётчики дефектов и не влияют на итог как
  подтверждённые; `confidence` модели не используется для ранжирования и оценки.
- **Не проверено** — для каждого требования явно:
  - не в графе: `FactGraph.excluded` (пустое, без источника);
  - не отправлено модели: `LLMAnalysis.skipped` с причиной, или режим `--rules-only`;
  - не участвовало ни в одной проверенной паре;
  - неоднозначные фрагменты не проверялись правилами формулировок.

### Проверка каждого требования (раздел 8)

Для каждого атомарного требования — карточка (`RequirementAssessment`):

- ID в отчёте, ID в документе, тип;
- подтверждённые дефекты: число по важности и ID замечаний (со ссылкой на раздел 4 или 7);
- гипотезы модели: число и категории (ссылка на разделы 5 и 6);
- участие в противоречиях: подтверждённые и потенциальные;
- покрытие: правила — да; модель — проверено / не проверено (причина) / режим
  `--rules-only`; проверка пар — была пара / кандидат не проверен / вне отбора;
- **категориальный статус** (не число):

  | Статус | Условие |
  | :--- | :--- |
  | Есть подтверждённые существенные дефекты | есть `verified` `major` или подтверждённое противоречие |
  | Есть подтверждённые незначительные дефекты | только `verified` `minor` |
  | Нужна проверка человеком | подтверждённых нет, но есть гипотезы или потенциальные противоречия |
  | Замечаний нет (правила и модель) | ничего нет; LLM-обзор этого требования выполнен |
  | Замечаний нет (только правила) | ничего нет; модель требование не проверяла |
  | Не проверено | требование вне графа (пустое, без источника) |

Формулировка «замечаний нет» обязательно с уточнением, чем проверено, и никогда не
«требование корректно».

Для больших документов раздел 8 — компактная таблица по всем требованиям (одна строка на
требование, без цитат: цитаты уже есть в разделах 4–7), отсортированная по месту в документе.

### Сводка (раздел 9)

Только счётчики вида «k из n», без процентов с десятыми и без «баллов»:

- требований (атомарных), неоднозначных фрагментов; требований по статусам раздела 8;
- подтверждённые дефекты по важности и по критериям ISO 29148 / IEEE 830 (`criterion`);
- гипотезы по категориям обзора и по типам связей;
- противоречия: подтверждённые и потенциальные;
- критерии приёмки: сколько, сценариев без ожидаемого результата, связь с требованиями;
- покрытие:
  - модель: требований k из n, пар k из m;
  - пары вне отбора и исключённые ограничением отбора;
  - режим запуска.

**Критичные дефекты** по ТЗ — «непроверяемые, противоречивые, неполные формулировки».
Правила важность `critical` не присваивают и этап 9 её **не придумывает**. В сводке это
явный список подтверждённых (`verified`) дефектов категорий:
- проверяемость: TST-*, ACC-01;
- полнота: CMP-*;
- согласованность: подтверждённые противоречия.

Отображение категорий в список — константа в коде с тестом.

### Итог (раздел 10)

Категориальный вердикт по **подтверждённым** фактам с явной оговоркой о покрытии:

| Вердикт | Условие |
| :--- | :--- |
| Начинать разработку не рекомендуется | есть подтверждённое противоречие или подтверждённый `major`-дефект проверяемости/полноты |
| Можно начинать после исправления замечаний | подтверждённые дефекты только `minor` и/или `major` других категорий |
| Подтверждённых препятствий не найдено | подтверждённых дефектов нет |

- Третий вердикт **всегда** сопровождается оговоркой: что не проверено (модель не
  использовалась, бюджет исчерпан, пары вне отбора), сколько гипотез ждут проверки
  человеком, и что это не доказательство корректности документа.
- Пороги вердикта — константы с тестами и описанием в README; без «магических» весов.
- Приоритет исправлений — подтверждённые дефекты по порядку:
  1. подтверждённые противоречия;
  2. важность (`major` → `minor`);
  3. категория (проверяемость → полнота → согласованность → однозначность → трассируемость);
  4. число затронутых требований;
  5. место в документе.

  Первые 10 и «ещё N». Отдельным списком «Проверить человеком» — гипотезы и потенциальные
  противоречия (без ранжирования по `confidence`).

### Требования к тестам

- Единичные тесты оценки на собственных документах:
  - каждая строка таблиц статусов и вердиктов;
  - CTR-02 и CON-03-«совместимые» не считаются подтверждёнными противоречиями;
  - `info` не считается дефектом;
  - гипотезы не влияют на вердикт;
  - `confidence` не влияет на порядок.
- Покрытие:
  - `--rules-only`: вердикт с оговоркой «модель не использовалась»;
  - бюджет LLM частичный, проверка пар выключена (`LLM_MAX_PAIR_REQUESTS=0`), ограничение
    отбора сработало.
- Пустой документ и документ без требований (только справочный текст); документ только с
  неоднозначными фрагментами.
- Отчёт:
  - разделы 1–7 побайтно совпадают с отчётом Stage 8 (кроме даты и версии) на собственных
    документах и на эталоне официального MD;
  - разделы 8–10 присутствуют в обоих режимах;
  - запрещённые формулировки отсутствуют: «документ корректен», «ошибок нет»,
    «противоречий нет», «все пары проверены».
- Детерминизм: повторный прогон и разные `PYTHONHASHSEED` дают одинаковый `Scorecard.to_json()`.
- CLI: строка итога в stdout; коды выхода прежние; при сбое провайдера (код 4) отчёт по-прежнему
  не пишется.

### Критерии приёмки Stage 9

- В отчёте есть разделы 8–10; каждое утверждение сводки и итога выводится из объектов
  предыдущих этапов и ссылается на ID замечаний или требований.
- Подтверждённое, гипотезы и непроверенное разделены везде; гипотезы не повышаются.
- Разделы 1–7 и эталон Stage 8 не изменились; все quality gates зелёные.
- README описывает статусы, вердикты, пороги и ограничения оценки.

### Ограничения и edge cases

- Документ без атомарных требований → сводка с нулями и вердикт «оценить нельзя:
  требования не выделены», а не «препятствий не найдено».
- Все гипотезы отклонены Gate → «гипотез, прошедших проверку цитат, нет», не «проблем нет».
- Одно требование в нескольких замечаниях и противоречиях — не дублировать в счётчиках
  требований (считать требования и замечания отдельно).
- Утверждения `X/1`, `X/2` — отдельные требования; составное `X` в карточки не входит (как в
  графе).
- Большие документы: раздел 8 не должен становиться неограниченно длинным — компактная
  строка на требование, без повторения цитат.

## Stage 10 — Evaluation

### Цель

Измерить качество самого валидатора на воспроизводимом наборе собственных документов и
честно описать, где он ошибается: ложные срабатывания, пропуски, стабильность, форматы,
производительность, поведение при сбоях API.

### Шаг 0: закрыть известный долг

README обещает исправить до Stage 10: `match_segmentations` на шаге «одинаковый ID» не
учитывает текст и может спарить разные требования при перенумерации. Исправить по TDD,
не меняя сегментацию и эталон.

### Методика

1. **Корпус** (новая папка `evaluation/corpus/`, только собственные тексты):
   - документы в разных доменах (библиотека, бронирование, банковские продукты
     собственными формулировками), 20–40 требований каждый;
   - в каждом — **внедрённые дефекты** с разметкой и **контрольные требования-ловушки**,
     которые не должны давать срабатываний:
     - число рядом с оценочным словом;
     - термин из глоссария;
     - отрицание;
     - разные сценарии;
     - разные параметры с похожими названиями;
     - одинаковые числа у разных объектов;
     - производные слова.
   - Разметка — отдельный файл `*.labels.json`: якорь требования (ID документа или
     уникальная цитата), ожидаемый `rule_id` или категория, ожидаемый статус
     (подтверждено / гипотеза / не должно сработать), для противоречий — пара и ожидаемый
     статус.
   - Разделить корпус на **dev** (на нём можно отлаживать) и **held-out test** (метрики
     итогового отчёта только по нему), чтобы не подгонять правила под данные.
2. **Метрики детерминированного слоя** (обоснованная разметка есть):
   - TP/FP/FN, precision и recall по каждому правилу и по категориям; макро-усреднение;
   - отдельно — частота срабатываний на ловушках (ложные срабатывания);
   - сегментация: число атомарных требований и роли на размеченном подмножестве;
   - противоречия: precision CTR-01 на ловушках-подконтекстах, recall на внедрённых
     конфликтах;
   - отбор кандидатов: recall размеченных связанных пар среди кандидатов, число кандидатов.
3. **LLM-слой** (смысловое качество требует реальной модели):
   - механика (схема, Gate, бюджеты, сбои) уже покрыта тестами — повторно не тестировать;
   - смысловая оценка — только на собственном корпусе, с моделью, доступной владельцу
     (реальный ключ или локальная Ollama); записывать провайдера, модель, версии промптов (`2`,
     `pair-1`), температуру 0;
   - метрики: доля гипотез, прошедших Gate; согласие гипотез с разметкой (precision);
     recall смысловых дефектов, которые правила не ловят; стабильность гипотез между 2–3
     повторами (пересечение множеств).
   - Если ключа нет — раздел LLM помечается «не измерено» с причиной, без выдуманных цифр.
4. **Форматы:** тот же корпус в MD, TXT, DOCX, PDF (генераторы по образцу `tests/builders.py`).
   Сравнить требования и замечания; ожидаемые различия (таблицы в TXT, заголовки в TXT без
   разметки) задокументировать.
5. **Стабильность:**
   - повтор ×N;
   - `PYTHONHASHSEED` 0/1/random;
   - перестановка требований: множество замечаний то же, порядок — по документу;
   - сравнение JSON результатов.
6. **Производительность и память:**
   - синтетические документы 50/200/1000/2000 требований и неблагоприятный случай для отбора
     кандидатов (общие слова почти у половины требований);
   - время по этапам: чтение, сегментация, lint, граф, quality, отчёт — и пиковая память
     (`tracemalloc` замедляет работу в 3–10 раз: время мерить без него, память — отдельно);
   - зафиксировать характеристики машины. Ориентир Stage 7.1 для построения графа без
     трассировки: 2000 требований — ≈0,3 с (обычный случай), ≈0,8 с (неблагоприятный).
7. **Сбои API** (через `StubServer`, без настоящей сети):
   - таймаут, 429 с `Retry-After`, 5xx, некорректный и пустой ответ, сбой посередине;
   - проверить коды выхода, отсутствие отчёта, понятные сообщения;
   - ключ (`FAKE_KEY`) не появляется ни в stdout/stderr, ни в отчёте.
8. **Официальный документ:**
   - можно прогонять локально (`--rules-only` или локальная модель) для сводных чисел;
   - **нельзя** превращать его дефекты в разметку корпуса, правила или тесты и коммитить его
     текст;
   - во внешний API — только с явного разрешения владельца проекта.

### Воспроизводимость

- `evaluation/run_evaluation.py` — один запуск строит все метрики. Вызывает функции конвейера
  напрямую (`load_document` → … → `assess`), а не разбирает Markdown.
- Вывод: машиночитаемый `evaluation/results/*.json` и итоговый `EVALUATION.md`.
- В результатах записаны: коммит Git, версия Python, версии зависимостей, параметры
  запуска, провайдер и модель (если были).
- Детерминированная часть даёт одинаковые числа при повторе.

### Формат итогового отчёта `EVALUATION.md`

1. Цель и конфигурация (коммит, окружение, машина).
2. Корпус: документы, число требований, дефектов и ловушек, dev/test.
3. Детерминированный слой: таблица по правилам (TP/FP/FN, precision, recall), по категориям.
4. Ложные срабатывания: примеры из корпуса с причиной.
5. Пропуски: примеры с причиной (что правила не умеют).
6. Противоречия и отбор кандидатов.
7. LLM-слой: метрики или «не измерено» с причиной.
8. Форматы, стабильность, производительность, память, сбои API.
9. Ограничения оценки и выводы; как воспроизвести.

### Требования к тестам Stage 10

- Тесты самой оценки: подсчёт TP/FP/FN на маленьком искусственном примере; загрузчик
  разметки отвергает якорь, которого нет в документе.
- Скрипт оценки не ходит в сеть без явного параметра; без ключа LLM-раздел помечается
  «не измерено».
- Полный набор тестов проекта остаётся зелёным; оценка не добавляет долгих тестов в
  обычный `pytest` (крупные замеры — только в скрипте).

### Критерии завершения Stage 10

- Корпус и разметка в репозитории; `run_evaluation.py` воспроизводит `EVALUATION.md`.
- Метрики на held-out наборе; ложные срабатывания и пропуски разобраны на примерах.
- Найденные дефекты валидатора исправлены по TDD в рамках этапа (без подгонки под корпус)
  или явно описаны как ограничения.
- Долг `match_segmentations` закрыт; quality gates зелёные; эталон не изменился без
  объяснения.
