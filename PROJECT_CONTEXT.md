## 1. Что это за проект

**AI Requirements Validator** — Python CLI-программа (ИИ-агент) для статической проверки
документа требований к программной системе. Проект сделан для хакатона
**BCC-HUB × MNU FinTech**. Техническое задание организаторов кратко:

- на входе — готовый документ требований (обязательно PDF, желательно и другие форматы);
- агент делит его на отдельные требования, оценивает каждое, а затем весь набор;
- критерии качества — ISO/IEC/IEEE 29148:2018 (5.2.5–5.2.6) и IEEE 830-1998 (4.3);
- результат — файл отчёта на русском: паспорт прогона, таблица нарезки (наш ID — ID из
  документа — краткая формулировка), оценка по требованиям, оценка набора, **сводка**
  (сколько требований и нарушений, перечень критичных дефектов) и **итог** (готов ли
  документ к началу разработки и тестирования, какие исправления приоритетны);
- у любого нарушения есть привязка к месту в документе, абстрактных выводов нет;
- запуск — одна команда с путём к документу и путём к отчёту; ключ модели хранится в `.env`,
  в корне лежит образец `.env.example`, ключи не публикуются.

Проверяемый документ организаторы выдают отдельно. **Он не входит в репозиторий** и не
должен туда попадать (см. HANDOFF.md, раздел «Официальный документ задания»).

### Вход, обработка, выход

| | |
| :--- | :--- |
| **Вход** | файл требований `.md`/`.markdown`, `.txt`, `.pdf` (с текстовым слоем), `.docx`; до 50 МБ |
| **Обработка** | чтение → сегментация на требования → детерминированные правила → Evidence Gate → (в стандартном режиме) LLM-обзор каждого требования → Fact Graph и проверка пар моделью → противоречия, критерии приёмки, полнота → отчёт |
| **Выход** | Markdown-отчёт на русском языке; код выхода 0/1/2/3/4; краткая сводка в stdout |
| **Для кого** | аналитики, архитекторы, тестировщики и руководители проектов, которым нужно ревью требований **до разработки**; жюри хакатона |

Речь о ревью текста требований до разработки (программа не тестируется): агент находит
двусмысленность, непроверяемость, пропуски, противоречия, нарушения трассируемости.

### Почему Proof-Carrying Findings

Языковая модель может ошибиться, придумать цитату или неверно понять текст. Поэтому проект
построен на принципе **Proof-Carrying Findings** («замечание несёт своё доказательство»):

1. Любое замечание — объект `Finding` с доказательствами `Evidence`: **точная цитата**
   (`fragment.text[start:end]`, символ в символ) и ссылки на блоки исходного файла
   (`SourceRef` → строка, страница, абзац DOCX, таблица/строка).
2. Каждое замечание проходит **Evidence Gate** (`validator/evidence.py`): цитата существует
   ровно в названном требовании этой версии документа (SHA-256), не обрезана посреди слова и
   не отрезает отрицание, место в файле вычислимо, замечание правила совпадает с записью
   каталога правил. Принцип **fail closed**: что нельзя проверить — отклоняется с причиной.
3. Статусы (`EvidenceStatus`):
   - `verified` — замечание **детерминированного правила**, все доказательства проверены:
     дефект следует из проверенных фактов документа;
   - `unverified` — **гипотеза LLM** с проверенной цитатой: цитата действительно из этого
     требования, но вывод модели о дефекте не проверен;
   - `rejected` — доказательства не подтвердились (показывается в отчёте с причинами).

**Почему гипотеза модели не считается доказанным дефектом.** Точная цитата доказывает только
происхождение текста, но не смысл вывода: модель могла неверно понять требование, не учесть
контекст или «увидеть» проблему, которой нет. Ни модель (схема ответа не принимает поля
статуса и происхождения), ни Gate не могут повысить гипотезу до `verified`. В отчёте гипотезы
всегда отделены от подтверждённых замечаний и помечены «не подтверждено».

## 2. Архитектура (фактическая)

Python ≥ 3.11 (проверено на 3.12.10), пакет `validator`. Зависимости времени выполнения:
`python-dotenv`, `markdown-it-py`, `pymupdf<2` (ветка 2.x тянет onnxruntime/numpy и
неизвестную лицензию разметки), `python-docx`. HTTP к моделям — только стандартная
библиотека (`urllib`), без SDK провайдеров. Разработка: `pytest`, `ruff`, `mypy --strict`.

### Конвейер (validator/cli.py → `main`)

```
load_settings (только в стандартном режиме; --rules-only не читает .env и ключи)
  → load_document(path)                     validator/ingest     → Document
  → segment_document(document)              validator/segmentation → Segmentation
  → run_lint(document, segmentation)        validator/lint       → LintResult (через Evidence Gate)
  → build_fact_graph(document, seg, lint)   validator/graph      → FactGraph
  → [стандартный режим] _run_llm:
        review_requirements(...)            validator/llm/review.py     → LLMAnalysis
        crosscheck_pairs(...)               validator/llm/crosscheck.py → CrossCheckAnalysis
        (один RateLimiter на оба вызова)
  → analyze_quality(document, seg, lint, graph) [+ .with_hypotheses(crosscheck.hypotheses)]
                                            validator/quality    → QualityResult
  → build_passport(...)                     validator/passport.py → RunPassport
  → assess(seg, lint, graph, quality, analysis=..., crosscheck=..., mode=...)
                                            validator/scoring    → Scorecard
  → render_report(passport, document, seg, lint, analysis,
                  graph=..., crosscheck=..., quality=..., scorecard=...)
                                            validator/report/markdown.py
  → ensure_source_unchanged(document)       файл не менялся во время проверки (иначе код 2)
  → write_text_atomic(output, report)       validator/report/writer.py
```

LLM-слой импортируется лениво (`from validator import llm` внутри `_run_llm`): в режиме
`--rules-only` он не загружается вовсе, сети нет.

### Сегментация и SourceRef

- `Document` — блоки (`heading`, `paragraph`, `list_item`, `table_header`, `table_row`,
  `code`) с дословным текстом, цепочкой разделов и местом `Location` (строки; страница и
  строки; абзац DOCX; таблица и строка).
- `Requirement` — фрагмент: `id`, дословный `text`, `normalized`, `role` (`requirement`,
  `ambiguous`, `explanation`, `example`, `reference`, `heading`, `table_header`, `code`),
  `category` (функциональное, API, критерий приёмки и т. д.), `sources: tuple[SourceRef]`,
  `section_path`, `doc_id`, `parent_id`/`children`, `references` (`req:Ф-2`,
  `section:…`, `unresolved:…`).
- `SourceRef(block, start, end, location)` — цитата это ровно
  `document.blocks[block].text[start:end]`.
- ID стабильны: ID из документа (`Ф-1`, `FR-2.1`) или `R-`/`F-` + 8 hex SHA-256
  нормализованного текста; `X~2` — дубль; `X/1` — утверждение внутри фрагмента. Порядок и
  раздел в ID не входят.
- `segmentation.atomic_requirements` — требования без дочерних требований (утверждения и
  неделимые фрагменты): именно их проверяют правила формулировок, LLM-обзор и граф.
- `verify_segmentation` машинно проверяет цитаты, места, покрытие блоков и нормализованный
  текст; Evidence Gate вызывает её перед проверкой замечаний.

### Детерминированные правила (Stage 3)

26 правил, каталог версии `1.0.0`: TST-01…05 (проверяемость), AMB-01…05 (однозначность),
CMP-01…07 (полнота), CON-01…03 (согласованность), TRC-01…06 (трассируемость). Таблица — в
README. У правила: ID, версия, категория, важность (`major`/`minor`/`info`; `critical`
правила не присваивают), критерий стандарта, условие срабатывания, объяснение, рекомендация.
Движок удаляет дубли и сортирует по месту в документе. Результат — `LintResult`
(JSON-схема `validator.lint/1`), принимает только `verified`-замечания правил.

### LLM-провайдеры (Stage 4)

`gemini` (по умолчанию модель `gemini-3.6-flash`), `openai`, `anthropic` (модель обязательна),
`ollama` (локально, без ключа). Единый контракт `LLMProvider.complete(LLMRequest)`.
Транспорт без перенаправлений, ключ только по https или на локальный адрес, ключ вырезается из
сообщений. Повтор только временных ошибок (таймаут, сеть, 429 с `Retry-After`, 5xx), не
больше `LLM_MAX_RETRIES`, пауза 1, 2, 4 … ≤ 30 с; `LLM_RPM` ограничивает частоту.
Сбой провайдера → код 4, отчёт **не пишется** (частичные результаты не сохраняются).

### LLM-обзор каждого требования (Stage 6)

`review_requirements`: один запрос на атомарное требование (промпт версии `2`), не больше
`LLM_MAX_REQUESTS` (по умолчанию 10, до 100). Модель получает ID, точный текст, SourceRef,
раздел и родительский фрагмент как недоверенные данные JSON. Строгая схема
`{"findings": [...]}`; категории `clarity`, `testability`, `completeness`, `atomicity`,
`undefined_term`, `subjectivity`, `missing_condition` → группа, критерий и важность выводятся
системой (`REVIEW_MAPPING`). Гипотеза принимается, только если ID — проверяемое требование, а
цитата один раз дословно и содержательно встречается в его тексте; затем Evidence Gate →
статус `unverified`. Непроверенные требования перечисляются с причиной (`budget`, `empty`,
`no_source`).

### Evidence Gate (Stage 5, расширен в Stage 7)

`gate_findings(findings, segmentation, document, rules=...)` → `GateResult` (`accepted` —
только правила, `unverified` — LLM, `rejected` с причинами, вердикт по каждому). Проверяется:
целостность сегментации, `document_sha256`, существование требований, точность цитат и
источников, совпадение с каталогом правил (`TrustedRule`), ограниченная область для
доказательства отсутствия (`AbsenceClaim`). Для связей (`Finding.relation` задан): ровно два
разных атомарных требования, вид `comparison`, две цитаты (источник, затем цель); правилом
подтверждается только зависимость по явной ссылке на ID.

### Fact Graph и проверка пар (Stage 7)

- Узлы — атомарные требования с текстом и корректным источником.
- Подтверждённые рёбра (`verified`): `depends_on` по явной ссылке на ID (правило XRF-01, вне
  каталога lint) и `conflicts_with` из подтверждённого CON-03.
- Пропуски с причиной: ссылка на составное требование, неоднозначный или отсутствующий ID.
- `crosscheck_pairs`: модель проверяет пары-кандидаты (по запросу на пару, бюджет
  `LLM_MAX_PAIR_REQUESTS`, по умолчанию 10, 0 — выключено), промпт `pair-1`, схема
  `{"relations": [...]}`; гипотезы связей — `unverified`; A→B и B→A для симметричных связей —
  одна связь.

### Отбор пар-кандидатов (Stage 7.1)

`validator/graph/candidates.py`: значимые слова (4+ букв, без ID, чисел, служебных,
модальных слов и отрицаний); формы одного слова объединяются через варианты основы
(закрытый список флексий) или общий корень из 7 букв; инвертированный индекс; кандидат —
пара минимум с двумя общими словами; дословные повторы и уже связанные пары исключаются.
Отбор ограничен `MAX_CANDIDATES = 1000` лучших пар (куча, память O(n + 1000)); найденные и
исключённые ограничением считаются точно. Отчёт различает: возможные, оценённые, найденные,
оставленные, исключённые ограничением, проверенные моделью пары и пары вне отбора.

### Противоречия, критерии приёмки, полнота (Stage 8)

`validator/quality` (без новых запросов к модели):

- CTR-01 (`verified`, подтверждённое противоречие) — утверждения «параметр — значение» с
  одинаковым названием в одном контексте (раздел, группа списка, таблица), значения —
  числовые величины с единицей, ограничения не пересекаются (машинный контрпример с
  пересчётом единиц);
- CTR-02 — то же в разных контекстах или без единицы: только потенциальное;
- пары CON-03 классифицируются числовым разбором; гипотезы модели `conflicts_with` — всегда
  потенциальные;
- ACC-01 — сценарий «Дано…» без шага «Тогда»; сводка замечаний и гипотез к критериям
  приёмки; связь критериев с требованиями по ссылкам на ID;
- полнота — сводка правил полноты, несведённых ссылок и гипотез модели; полнота документа
  не утверждается.

### CLI и коды выхода

```
python -m validator <документ> <отчёт.md> [--rules-only] [--provider P] [--model M] [--version]
```

`0` — успех (замечания — не ошибка); `1` — внутренняя ошибка; `2` — входной файл, путь
отчёта, неверные параметры, файл изменился во время проверки; `3` — настройка (нет ключа,
неизвестный провайдер, модель не найдена); `4` — сбой провайдера, отчёт не пишется.
`--rules-only` несовместим с `--provider`/`--model`.

Переменные `.env`: `LLM_PROVIDER`, `GEMINI_API_KEY`/`GEMINI_MODEL`, `OPENAI_API_KEY`/
`OPENAI_MODEL`, `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL`, `OLLAMA_BASE_URL`/`OLLAMA_MODEL`,
`LLM_BASE_URL`, `LLM_TEMPERATURE`, `LLM_TIMEOUT_SECONDS`, `LLM_MAX_RETRIES`, `LLM_RPM`,
`LLM_MAX_REQUESTS`, `LLM_MAX_PAIR_REQUESTS`, `LLM_MAX_OUTPUT_TOKENS`.

## 4. Инварианты — что нельзя нарушать

1. Замечание без проверяемого доказательства в отчёт как замечание не попадает.
2. `verified` — только детерминированные правила, прошедшие Evidence Gate; гипотезы LLM
   всегда `unverified`. Evidence Gate не ослаблять ради прохождения тестов.
3. Цитата — точный срез текста; нормализованный текст доказательством не является.
4. В отчёте не утверждать «документ корректен», «противоречий нет», «все пары проверены»,
   если соответствующая проверка не выполнена полностью; непроверенное перечислять.
5. `--rules-only` не читает `.env`, не загружает LLM-слой и не обращается к сети.
6. Сбой провайдера — код 4 без отчёта; бюджеты (`LLM_MAX_REQUESTS`,
   `LLM_MAX_PAIR_REQUESTS`), `LLM_RPM`, повторы и таймауты не обходить.
7. Результат детерминирован: повторный прогон и любой `PYTHONHASHSEED` дают тот же отчёт
   (кроме даты и версии).
8. Новые правила, которые не должны менять эталон разделов 1–6, делаются вне каталога lint
   (как XRF-01, CTR-01, ACC-01) и проходят Gate со своей записью `TrustedRule`.
9. Дефекты официального документа не превращаются в правила, исключения или тестовые
   данные; официальный документ не отправляется во внешние API без явного разрешения
   владельца проекта.
10. Ключи — только в `.env` (не в Git); ключ не печатается и не логируется.

## 5. Известные ограничения и открытые долги

- Реальный прогон с настоящими ключами API не выполнялся: стандартный режим проверен на
  `FakeProvider` и локальной HTTP-заглушке. Названия моделей по умолчанию нужно проверить на
  реальном ключе.
- Сегментация не делит предложения по союзам; глубина списков учитывается только через «:».
- Отбор кандидатов — эвристика без морфологического словаря.
- CTR-01 сравнивает только утверждения «параметр — значение» с числовым значением; числа в
  свободном тексте сравнивает только модель.
- Сценарии приёмки распознаются по ключевым словам в начале пункта.
- Строка `.validator_cache/` в `.gitignore` зарезервирована: кэш ответов LLM не реализован.
- Пороги вердикта Stage 9 фиксированы в коде и не настраиваются; итог отражает только
  подтверждённое правилами.
- Оценка (`EVALUATION.md`): пропуски из-за синонимов вне словарей; ACC-01 и CMP-04
  зависят от порядка пунктов; строки таблиц вне раздела требований не узлы графа.
  Смысловое качество LLM-слоя не измерено.
- Сегментация растёт примерно квадратично: 1000 требований — около 20 с, 2000 — около
  80–105 с (EVALUATION.md, раздел 8); документы на десятки требований — доли секунды.
